# Tech stack and architecture

> When to read: before structural changes, new components or new dependencies.

## Tech stack

- Language/runtime: Dart 3.13 / Flutter 3.47 (stable). SDK constraint in `pubspec.yaml`.
- Target: Android first (minSdk see open decisions). Code must stay iOS-capable; iOS-specific features are out of scope.
- State management: **Riverpod** (`flutter_riverpod`) – chosen because providers can be overridden with fakes (clock, keys, speech, video) in unit and widget tests without a widget tree.
- Persistence: local SQLite via **sqflite** with hand-written SQL. Schema migrations are an append-only list in `lib/core/database.dart` (`migrations[n]` creates version n+1). Chosen over drift to avoid code generation/build_runner; tests use `sqflite_common_ffi` with an in-memory DB.
- Localization: Flutter `gen-l10n` with ARB files in `lib/l10n/` (`l10n.yaml`); **English is the template/fallback**, German is the translation. Generated `app_localizations*.dart` are committed; after editing ARB files run `flutter gen-l10n`.
- `speech_to_text` – push-to-talk dictation of steps (platform recognizer, no own model).
- `wakelock_plus` – keep the screen on while recording.
- `video_player` – video playback (ExoPlayer) for video studies; `file_picker` – choosing videos (and backup files).
- `excel` – .xlsx export; `share_plus` – system share sheet for export/backup files. `shareParamsFor` (`export/platform/file_sharer.dart`) sets the share subject to the file name with extension, because Google Drive names saved files after the subject.
- `pdf` – PDF report (pure Dart, built-in Latin-1 fonts; shared via the share sheet instead of the `printing` plugin). Characters outside Latin-1 are mapped in `_latin1` (e.g. `Δ` → `Delta`).

## Architecture

- **Feature-first structure** under `lib/`: each feature (e.g. `study`, `recording`, `analysis`, `video`, `export`, `settings`) has `domain/` (pure Dart), `data/` (repositories, DB), `presentation/` (widgets, providers).
- **Domain is pure Dart**: measurement engine, statistics and export table building have no Flutter imports, so they are fully unit-testable.
- **Time source**: the engine reads time through a `Clock` interface (monotonic, e.g. `Stopwatch`-based). Video studies plug in a video-position time source. Durations are stored as integer microseconds; unit conversion (HM, s, mm:ss.SSS, TMU) happens only in formatters.
- **Platform abstractions**: hardware volume keys (Android platform channel), speech recognition, video playback, video frame decoding and the foreground service each sit behind a Dart interface with a fake in tests.
- **External links** (`core/url_opener.dart`): `UrlOpener` (`AndroidUrlOpener`, `urlOpenerProvider`, `FakeUrlOpener` in tests) asks `MainActivity.kt` (method `openUrl` on `dev.cyclescope/platform`) to open an `https` link in the browser with an `ACTION_VIEW` intent; it returns false when no app can open it. No `url_launcher` dependency and no INTERNET permission: the app itself still makes no network call. Used by the GitHub logo in the home app bar (`study/presentation/github_logo.dart`: `GitHubLogo` paints the Octicons mark as a path in the icon theme's color, `repositoryUrl`); a failed open shows a snack bar.
- **Frame decoding** (`video/platform/frame_source.dart` → `FrameDecoder.kt`, channel `dev.cyclescope/frames`): `MediaMetadataRetriever.getFramesAtIndex` (API 28+) decodes JPEG frames (longest side 1280 px) on a worker thread. `FrameCache` (pure Dart, `video/domain/frame_cache.dart`) keeps the frames within 8 of the position (forward first) and evicts far ones; `FrameTiming` converts time ↔ frame index with the real frame rate (frame count / duration). Frame stepping shows the cached frame above the player while it seeks; play or any other seek hides it. Without decoder support stepping falls back to 30 fps player seeks.
- **Data model (core)**: Study (name, description, mode) → StepDefinition (position, name) → Measurement (cycle number, step id, start, end, type `normal | special`, note). Measurements reference steps by id, never by position.
- **Groups** (`lib/group/`, migration v9): `study_group` (name, description, created_at). A study belongs to at most one group (`study.group_id`, `ON DELETE SET NULL` – deleting a group keeps its studies) at `study.group_position` (0-based order, e.g. machine order of a line). `GroupRepository` creates/updates/deletes groups, moves studies (appended at the end; null = no group) and sets the order; `StudyRepository.listStudies(groupId:)` lists the members in order and `StudySummary.groupName` names the group. `StudyRepository.copyStudy` duplicates a study with steps and times (step ids remapped), optionally into a group. "In several groups" is done by copying.
- **Crash safety**: every completed measurement and every engine state change is persisted immediately.

## App wiring

- `main()` opens the database and overrides `databaseProvider`; all other providers live in `lib/core/providers.dart` or the feature's `presentation/` folder.
- Lists are `FutureProvider`s that are invalidated after writes (sqflite has no change streams).
- Screens with live state use a `ChangeNotifier` controller (e.g. `RecordingController`) that reads its dependencies from providers once; Riverpod is the DI/override mechanism. Never use `ref` in `dispose()`.
- Platform side effects (haptics, wake lock, later keys/notifications) go through interfaces in `lib/core/platform.dart`, provided via `deviceFeedbackProvider` etc.
- Settings: `settingsProvider` (Riverpod `Notifier`) backed by the `settings` table; loaded in `main()` and injected via `initialSettingsProvider`. Providers that depend on settings (`deviceFeedbackProvider`, `recordingNotifierProvider`) watch it.
- Wall-clock timestamps (created/active) come from `wallClockProvider`, never directly from `DateTime.now()` in widgets.
- Video studies without steps have `study.steps_open = 1` (migration v7): `RecordingController.mark()` appends a step (and rebuilds the engine from its snapshot) while on the last step; `closeCycle()` wraps to the next cycle and clears the flag (`StudyRepository.closeSteps`). With fixed steps `closeCycle()` ends the cycle early via `RecordingEngine.endCycle()` (closes the current step, next cycle starts at step 1). `StudyMode.definesStepsUpfront` says which modes ask for steps on creation. Markers may not lie before the last marker (`canMarkAt`); so that deleted cycles or a new video never block positions, `RecordingController.resetMarkers()` drops the open marker run (engine back to idle, stored times kept). It runs when a video study's deleted cycle contains the marker the open step started at (or is the running cycle) and whenever the video is replaced; replacing a video with recorded cycles first asks whether to delete them (`deleteAllMeasurements()`) or keep them.
- **Revisions** (`lib/revision/`, migration v10): every stored measurement gets `measurement.recorded_at` (wall clock ms from `wallClockProvider`, injected into `MeasurementRepository(now:)`; NULL for older rows). `study.revision` is the number of the current measurement round (starts at 1). `RevisionRepository.startNewRevision` archives the current steps and times into `revision` / `revision_step` / `revision_measurement` (full snapshot; `revision_step.step_id` keeps the step's id in the study, without foreign key), deletes the times and the run state and increments `study.revision` – all in one transaction; without times nothing happens. `lastRecordedAt` = newest `recorded_at` of the current times (fallback `last_active_at` for old data). `RevisionComparison.compare` (pure Dart) matches steps by id, else by name, and gives real step/cycle time deltas. `RevisionsScreen` (history icon in the recording screen, study menu in the video screen) shows the current round, starts a new one (only when idle) and the deviations of each archived revision; it pops with the new number and the screen calls `controller.load()`. `copyStudy` copies the revisions too (ids of deleted steps become negative).
- Stale measurements: `openStudy` (`app.dart`, also used by the group screens) calls `offerNewRevisionIfStale` before the screen opens. If the last measurement (`lastRecordedAt`) is older than `AppSettings.staleDays` (default 10, 0 = off; `isMeasurementStale` in `revision/domain/staleness.dart`) it asks "New measurement" (→ `startNewRevision`) or "Continue". Skipped for video studies and while a run state exists.
- **Exports and group report** (`lib/export/domain/`): `ExportInput` optionally carries the latest archived revision (`previous`) and derives `lastMeasuredAt` (newest `recordedAt`, fallback `lastActiveAt`) and `comparison`. `ExportLabels.revision` (`RevisionLabels`, optional so old call sites keep working) adds the "Revision" and "Last measurement" lines to CSV/Excel/PDF and the PDF section "Deviation from revision N". `GroupReportInput` = group + one `ExportInput` per study in group order + `GroupReportLabels`; `buildGroupXlsx` writes an overview sheet and one sheet per study (`studySheetNames`: "<pos> <name>", max. 31 chars, no `[]:*?/\`, unique), `buildGroupPdf` an overview page and every study from a new page (shared `_studyWidgets`, page numbers over the whole document). UI: `GroupExportButton` in the group screen (unit = default unit, method per study or default).
- Backup (`lib/backup/data/backup_service.dart`): JSON `cyclescope-backup` version 2 = v1 plus `groups` (ref, name, description, createdAt), per study `groupRef`/`groupPosition`/`revision`, `recordedAt` per time and `revisions` (with `steps[].stepRef` = the study's step refs, ids of deleted steps kept). v1 files still import. Merging reuses groups by name and appends imported studies behind the group's existing ones (relative order kept); replace also clears groups and revisions. Not included: run state, settings, video files.
- **Line analysis** (`group/domain/line_analysis.dart`, pure Dart): `LineAnalysis.of(stations)` looks at a group as a line in group order – sum of the station real cycle times (processing lead time, no buffers), line cycle time = bottleneck (max), balance = sum / (measured stations × bottleneck), output per hour, waiting time per station, step segments scaled to the station cycle time, comparison with the previous revisions (only if every measured station has one). Stations without complete cycles (step timer, no times) are listed but not counted. `GroupReportInput.line` builds it from the report data; `loadGroupReport()` (`export_menu.dart`) loads the data for the report and the `LineScreen` (key figures, `YamazumiPainter` stacked bars with dashed bottleneck line, station list), opened from the group screen.
- **Excel look** (`lib/export/domain/xlsx_layout.dart`): every sheet of every workbook is written through `SheetLayout` (`title`, `section`, `note`, `keyValue`, `cells`, `header`, `row(total:)`, `gap`, `finish`). It owns the row cursor and the look: Calibri 11, brand-coloured title/section headings, bold key-figure labels, table headers in white on the brand colour `0B6B8A`, banded rows with thin grey borders, a tinted bold total row, blue underlined links (`sheetLink`), row heights, real empty rows between blocks (`gap`; `appendRow([])` of the excel package is a no-op) and column widths from the measured content (min 9, max 50; table texts over 46 characters are measured as 46 and wrap only when `finish` finds them wider than their final column – an average text character counts as 0.9 of the "0" Excel measures widths in – so only rows that really need more lines get higher; long key-figure texts and notes overflow instead of widening a column, except on a sheet without tables (nothing right of column B, e.g. Contents), where they widen column B up to 60 and wrap beyond that). Numbers get fixed decimals via `fixed(value, decimals)` (times: 3, HM: 2, TMU/percent: 1); headers of number columns are right-aligned (a column without values counts as numbers when its title ends with a unit `]`). Key-figure numbers use the format `0.000* ` (fill of spaces) so they stand left like texts – the excel package cannot write a left alignment. Other quirks of excel 4.0.6 handled there: the `CellStyle` constructor ignores `underline` (set by the setter), and `updateCell` resets the style, so value and style are always written together. New sheets must use `SheetLayout`, not `appendRow`.
- **Complete group report** (Task_25): `buildGroupReportPdf` = cover (group, line key figures) with a clickable table of contents (page numbers, `pw.Link` to `pw.Outline` anchors, which are also PDF bookmarks), line analysis (bars per station, station table), overview and every study from a new page. The document is laid out twice: pass 1 records the first page of every section (`doc.document.pdfPageList.pages.length` after each `addPage`), pass 2 prints them. `buildGroupReportXlsx` = sheets Contents (`HYPERLINK("#'sheet'!A1", ...)` formulas), Line analysis (station cycle times as references to the real cycle time cell of each study sheet, share/waiting/Δ, SUM, MAX, INDEX/MATCH bottleneck, balance, output per hour as formulas), Overview (extra link column) and the study sheets (back link in row 1). The excel package writes formulas without cached values; Excel/LibreOffice compute them on opening. Row numbers for formulas come from `SheetLayout` (`nextRow`, return value of `keyValue`/`row`), never from `maxRows`. The compact builders `buildGroupPdf`/`buildGroupXlsx` stay as the "compact" export option.
- **Parallel machines** (migration v11): `study.parallel` = works in parallel with the group member before it; consecutive parallel members form one station (`stationGroups`, labels "2a/2b" via `stationLabels` in `group/domain/stations.dart`). `GroupRepository.setParallel`; moving into/out of a group and copying reset the flag; backup field `parallel` (optional, format stays v2). A "machine with fixed cycle time" (`MachineService`, `machineServiceProvider`) is a simple study with exactly one lap of the typed duration (`parseTimeInput`, unit = default unit, stopwatch typed as seconds); "Enter cycle time" archives the previous times as a revision and stores a new lap.
- **Parallel stations and failure risk** (Task_27): `LineAnalysis.of` builds stations from consecutive parallel inputs (`LineStationInput.parallel`, `stationGroups`). A station holds its `LineMachine`s; its effective cycle time is `parallelCycleTime` = 1 / Σ(1 / machine cycle time) over the measured machines, its `leadTime` the mean machine cycle time (one part passes one machine). `totalTime` = Σ effective station times (basis of share and balance), `leadTime` = Σ station lead times. `FailureRisk.of(line)` (pure Dart) gives, per measured machine, the line output while it is down (minimum station capacity, a station without a remaining machine → 0 = standstill) and the loss, sorted by loss; `singlePoints` = stations whose only machine stops the line. `LineScreen` shows lead time, machines per station ("×n" in the bar) and the failure risk list.
- **Reports with parallel stations and failure risk** (Task_28): the Excel line sheet has one row per station (`stationGroups` over the entries); a parallel station's cycle time is the formula `1/(1/'sheet a'!B8+1/'sheet b'!B8+...)`, its name the machine names with "(×n)". `LineReportLabels.risk` (`RiskReportLabels`, optional) adds the failure risk sheet (Excel, linked from Contents) and chapter (PDF, in the table of contents) built from `FailureRisk`. The app adds them when the line has at least one parallel station.
- **Buffers** (migration v12): a buffer before a station is stored on the station's first member (`study.buffer_capacity` 0 = none, `buffer_store_us`, `buffer_retrieve_us`; `Study.hasBuffer`). Never before the first station. `GroupRepository.setBuffer/removeBuffer`; switching a member to parallel, moving and copying drop it (the first machine of a parallel station hands it to the next one, see "Stations stay together"); backup fields `bufferCapacity/bufferStore/bufferRetrieve` (optional, format v2). The group screen shows the buffer as its own card above the station (tap = edit/remove, `showBufferDialog`), menu item "Insert buffer before". Semantics (simulation, Task_30): the buffer stores only on a jam, its own machine spends the store/retrieve time, and it empties itself when the next station is free.
- **Line simulation** (`group/domain/line_simulation.dart`, pure Dart, Task_30): deterministic event-driven simulation of `SimStation`s (machines with their real cycle time, parallel machines share the work) over a horizon. Raw parts are unlimited, the line starts empty, there is no space between stations without a buffer (a finished part blocks its machine). A `SimBuffer` before a station is its own machine with one place in front of the station: it stores a waiting part only on a real jam (the station stays busy longer than storing takes), otherwise brings stored parts to the place in front of the station while it works; that part goes before parts on the conveyor. `SimFailure` = one machine down from a start time for a duration (a part in work finishes after the repair). `SimResult`: output, per station busy/blocked/down time and utilization, per buffer max/end level, stores, retrieves, handling time. `failureScenarios` compares every machine failure with and without buffers. `LineSimulation.fromLine(LineAnalysis)` takes the measured stations; `LineStationInput.buffer`/`LineStation.bufferBefore` (`LineBuffer`) carry the buffers. A 24 h run with ~7000 parts and all scenarios takes well under a second. Time accounts: every machine keeps its stops as merged intervals; stopped time is neither busy nor blocked time (busy and blocked are counted without the stops inside them, all clipped to the horizon), so busy + blocked + down never exceed the period. `run` throws an `ArgumentError` for a machine with a cycle time ≤ 0 (it would finish parts without time passing); `LineAnalysis` treats a real cycle time below 1 µs as "not measured", so `fromLine` never produces one, and `parseTimeInput` rejects typed times below 1 µs.
- **Simulation screen** (Task_31): `SimulationScreen` (play icon in the line screen) runs `LineSimulation.fromLine(loadGroupReport(...).line)` over a shift (`AppSettings.shiftMinutes`, default 480), 24 h or a free number of hours, optionally with one machine failing (start in hours, default a quarter of the period; duration in minutes, default `AppSettings.failureMinutes` = 30). Stations are labelled with their number in the line (stations without times are not simulated but keep their number). It shows parts without/with the failure, lost parts, lost parts without buffers and the parts saved by the buffers, per buffer fill/moves/handling time and per station utilization, blocked and down time (`formatDuration`). The line screen lists buffers between the stations.
- **Reports with buffers and simulated risk** (Task_32): `GroupReportInput.simulationHorizonMicros/simulationFailureMicros` (the app passes shift length and assumed failure duration from the settings) give `failureScenarios` (only when the line has buffers; failure after a quarter of the period). `LineReportLabels.buffers` (`BufferReportLabels`) adds a buffer table to the line chapter/sheet; `RiskReportLabels.withSimulation` adds the columns "lost without/with buffers" and a note to the failure risk chapter/sheet. The app adds the failure risk when the line has parallel machines or buffers.
- **Conveyors** (Task_33, migration v13): `study.conveyor_capacity` (0 = none) and `conveyor_transport_us` on a station's first member (like the buffer; dropped on parallel/move/copy; backup fields `conveyorCapacity/conveyorTransport`). `LineConveyor`/`LineStation.conveyorBefore`; the lead time of one part includes the transport times. Simulation: `SimConveyor` is a FIFO with a capacity counting moving and jammed parts; a finished part leaves its machine while there is room and reaches the next station after the transport time. With a conveyor, a buffer at the same place stores only when the conveyor is full and retrieves onto the conveyor (in front of the station) as soon as there is room. `withoutBuffers()` keeps the conveyors. Group screen "Insert conveyor before", conveyor cards in group, line and simulation screens, conveyor columns in the report's connection table (`BufferReportLabels.conveyorPlaces/conveyorTime`).
- **Special cycles and planned stops** (Task_34, migration v14): table `special_cycle` (study, name, kind `parts`/`time`, interval = parts or µs, duration µs), `SpecialCycleRepository` (`specialCycleRepositoryProvider`), copied with the study and part of the backup (`specialCycles`). `effectiveCycleTime(base, cycles)` = (base + Σ duration/N) / `availability` (1 − Σ duration/interval). `LineStationInput.specialCycles` → `LineMachine.cycleTime` is the effective time, `baseCycleTime` the measured one; line figures and the failure risk use the effective time. Simulation: `SimMachine.specialCycles` – every N-th part takes the extra time; planned stops are stop windows like a failure, the first after half the interval, then every interval. `GroupReportInput.specialCycles` (per study id, loaded by `loadGroupReport`). UI: member menu "Special cycles & stops…" → `SpecialCyclesScreen`; reports list them with measured and effective cycle time (`SpecialReportLabels`). The Excel line sheet writes a machine's station cycle time as `(study cell + extra time per part) / availability` (`extraPerPart`, `availability` as constants in the report unit), so its line figures match the app and the PDF. The dialog rejects a planned stop that is not shorter than its interval (`stopTooLong`).
- **Demo data** (`lib/demo/`, Task_35): `DemoDataService.load(DemoTexts)` adds a sample line through the normal repositories only (no own SQL, no migration): group "Demo: housing line" with 9 members / 6 stations – saw (typed 38 s, blade change every 8 h), milling centre 1 (time study, revision 1 archived, special time, special cycles) parallel to milling centre 2 (typed 110 s, bottleneck station, buffer before), washer (conveyor before), assembly (time study with an outlier, IQR method, revision, special time), test benches 1–3 in parallel (buffer before, calibration every 200 parts), packing (simple study with laps, conveyor before) – plus a step-timer changeover study outside the group. Times are deterministic, timestamps relative to `wallClockProvider` (current times 1–2 days old, so no stale prompt). Names come from l10n (`demoTextsOf(AppLocalizations)`), i.e. the app language at load time. Settings → Data → `DemoDataTile` (confirmation dialog, invalidates the study and group lists). Each load adds a new copy; nothing is replaced.
- **Stations stay together** (review after Task_35): "parallel" means parallel to the member before, so every way a member leaves its place must look after the members behind it.
  - Leaving the group (`GroupRepository.moveToGroup`, `StudyRepository.deleteStudy`) calls `StudyRepository.handOverStation`: if the member is the first machine of a station with parallel machines, the next machine becomes the first one and takes over the buffer and conveyor (`stationLinkColumns`).
  - Reordering: `GroupRepository.reorder(groupId, ids, moved: id)` (the group screen always passes the moved member) applies `parallelAfterMove` (`group/domain/stations.dart`, pure Dart): a first machine that moves away hands its station over as above; the moved member is parallel only when it was dropped inside a station (the member behind it is parallel) and then loses its own buffer/conveyor; anywhere else it is a station of its own. Without `moved` only the positions change.
- **Video files** (`video/platform/video_files.dart`): `VideoFiles` (`LocalVideoFiles`, `videoFilesProvider`, `FakeVideoFiles` in tests) deletes copied videos. `deleteUnusedVideo` (`video/data/video_cleanup.dart`) deletes a file only when no study uses its path any more (copies of a study share the file); called after deleting a study, after replacing a video (once the player has opened the new one) and when the "keep cycles?" question is cancelled (the copy made by the picker).
- **Fresh times carry their timestamp**: `MeasurementRepository.store` returns the stored `Measurement` including `recordedAt`; `RecordingSession` uses it, so exports right after recording show the right "last measurement". Anything that copies a `Measurement` (`updateNote`, `moveBoundary`) must pass `recordedAt` on.
- **Undo of a marker with special times**: `RecordingEngine.rewindTo(m, specials:)` continues behind the last special time of the step with the time worked before it, so the special time is not counted into the step again; `RecordingController.undoLastMarker` passes the special times of that step.
- Groups UI: home app bar → `GroupListScreen` → `GroupScreen` (reorderable list with drag handles plus "Move up/down" in the item menu, add new/existing studies, move/copy/remove). Shared dialogs in `group/presentation/group_dialogs.dart` (`pickGroup`, `moveStudyToGroup`, `copyStudyToGroup`); the study card menu on the home screen uses them too. `OpenStudy` callbacks are passed down from `app.dart`.
- Study notes: `study.notes` (migration v8, `TEXT NOT NULL DEFAULT ''`), edited in the analysis tab via `RecordingController.setNotes()` (which also refreshes `study`, so an export right after typing sees them) and written by the CSV/Excel header block and the PDF report; part of the backup (`notes`, optional on import). The analysis unit chip calls `RecordingController.onAnalysisUnitChosen`, which the screens wire to save `AppSettings.defaultUnit`.
- Dictation (`DictationButton`) queues recognizer calls: a release during start stops once started, a new press waits for the previous session's result. `SystemSpeechInput.stop()` waits (bounded) for the recognizer's "done" status, because Android's recognizer is busy until then.

## Environment

- Dependencies only via `flutter pub add` / `flutter pub get`. No `.env` needed (no external services).
- Release signing: the only secret of the project. `android/app/build.gradle.kts` signs release builds with the key from `android/key.properties` (template: `android/key.properties.example`; the real file, `*.jks` and `*.keystore` are git-ignored). Without the file, release builds use the debug key.
- The release keystore lives outside the repository and must be backed up by the owner: without it no update of an installed app is possible. GitHub secrets used by `.github/workflows/release.yml`: `ANDROID_KEYSTORE_BASE64` (base64 of the `.jks`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
- Releases: pushing a tag `vX.Y.Z` runs the tests, builds `flutter build apk --release` (version name from the tag, version code = workflow run number) and publishes the APK as a GitHub release.
- Google Play: application ID `dev.cyclescope.cyclescope` (fixed once published), launcher label `CycleScope`. Upload an app bundle (`flutter build appbundle --release`, signed with the release key above as upload key; Play App Signing holds the app signing key). Store graphics come from `python tool/generate_store_assets.py`, which wraps `screenshots/<lang>/` in 1080 × 1920 frames and writes the icon and feature graphic into the local, git-ignored `store/` folder (listing texts and console answers are kept there by hand).
- Play upload: fastlane in `android/` (`Gemfile`, `fastlane/Fastfile`, lane `internal` with options `track:` and `status:`). It asks Play for the highest version code on all tracks, builds `flutter build appbundle --build-number <max+1>` and uploads the bundle (no metadata or images; the store listing is maintained in the console). CI: `.github/workflows/play.yml`, started by hand (track internal/alpha/beta/production, status draft/completed), runs the tests first. Secrets: the `ANDROID_*` signing secrets (shared composite action `.github/actions/android-signing`, also used by `release.yml`) and `PLAY_SERVICE_ACCOUNT_JSON` (JSON key of a Google Cloud service account invited in the Play Console with release rights for the app). Ruby/fastlane are only needed in CI.
- Privacy policy (required by Google Play): `site/privacy/index.html`, published with the small landing page `site/` by `.github/workflows/pages.yml` (GitHub Pages, source "GitHub Actions") at https://sphaerox.github.io/Serienmessung/privacy/. Keep it in line with the app's permissions and data handling whenever those change.
- Android application id: `dev.cyclescope.cyclescope`, Dart package name `cyclescope`.
