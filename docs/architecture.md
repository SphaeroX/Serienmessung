# Tech stack and architecture

> When to read: before structural changes, new components or new dependencies.

## Tech stack

- Language/runtime: Dart 3.13 / Flutter 3.47 (stable). SDK constraint in `pubspec.yaml`.
- Target: Android (minSdk see open decisions, application id `dev.cyclescope.cyclescope`) and iOS (bundle id `com.boundfoxstudios.apps.cyclescope`, deployment target 15.0, iPhone and iPad).
- State management: **Riverpod** (`flutter_riverpod`) – chosen because providers can be overridden with fakes (clock, keys, speech, video) in unit and widget tests without a widget tree.
- Persistence: local SQLite via **sqflite** with hand-written SQL. Schema migrations are an append-only list in `lib/core/database.dart` (`migrations[n]` creates version n+1). Chosen over drift to avoid code generation/build_runner; tests use `sqflite_common_ffi` with an in-memory DB.
- Localization: Flutter `gen-l10n` with ARB files in `lib/l10n/` (`l10n.yaml`); **English is the template/fallback**, German is the translation. Generated `app_localizations*.dart` are committed; after editing ARB files run `flutter gen-l10n`.
- `speech_to_text` – push-to-talk dictation of steps (platform recognizer, no own model).
- `wakelock_plus` – keep the screen on while recording.
- `video_player` – video playback (ExoPlayer on Android, AVPlayer on iOS) for video studies; `file_picker` – choosing videos (and backup files).
- `excel` – .xlsx export; `share_plus` – system share sheet for export/backup files. `shareParamsFor` (`export/platform/file_sharer.dart`) sets the share subject to the file name with extension, because Google Drive names saved files after the subject.
- `pdf` – PDF report (pure Dart, built-in Latin-1 fonts; shared via the share sheet instead of the `printing` plugin). Characters outside Latin-1 are mapped in `_latin1` (e.g. `Δ` → `Delta`).

## Architecture

- **Feature-first structure** under `lib/`: each feature (e.g. `study`, `recording`, `analysis`, `video`, `export`, `settings`) has `domain/` (pure Dart), `data/` (repositories, DB), `presentation/` (widgets, providers).
- **Domain is pure Dart**: measurement engine, statistics and export table building have no Flutter imports, so they are fully unit-testable.
- **Time source**: the engine reads time through a `Clock` interface (monotonic, e.g. `Stopwatch`-based). Video studies plug in a video-position time source. Durations are stored as integer microseconds; unit conversion (HM, s, mm:ss.SSS, TMU) happens only in formatters.
  - `MonotonicClock` (`core/clock.dart`) starts at the platform time that keeps counting during sleep (`elapsedRealtimeMicros` on `dev.cyclescope/platform`: Android `SystemClock.elapsedRealtimeNanos`, iOS `CLOCK_MONOTONIC_RAW`; read in `main()`) and counts on with a `Stopwatch`, which stands still while the device sleeps. It is a `SyncableClock`: `syncTo(platformMicros)` moves it forward to the platform time and never back (jitter); `nowMicros()` never returns less than before. `syncClockTo(clock, µs)` ignores clocks that cannot sync (`FakeClock`). The tick source is injectable (`ticks:`) for tests (`FakeTicks` in `tests/fakes/fake_platform_time.dart`).
  - The clock is synced (Task_47) on every volume key event (`MainActivity.kt` sends `realtimeMicros` next to `ageMicros`; the press time is `realtimeMicros − ageMicros`), on every notification button (event on `dev.cyclescope/notification_actions` is a map `{action, realtimeMicros}`; plain strings are still read; `AndroidRecordingNotifier` implements `TimedNotificationActions`, `notificationActionsOf(notifier)` gives `NotificationAction(name, atMicros)` and `RecordingScreen` runs `next(at:)`/`startStop(at:)` with that time), and when the app returns to the foreground (`ClockResumeSync` wraps the app once, reads `platformTimeProvider` = `PlatformTime`/`ChannelPlatformTime`, `FakePlatformTime` in tests; Android and iOS). Known gap, accepted: a tap on the screen in the first milliseconds after waking up, before the resume sync is back, can still see the clock without the sleep.
  - **Reboot rule** (`RecordingController.load`): a saved run state counts as interrupted by a device reboot (run dropped, stored times kept, `interruptedByReboot`) when the clock is below the saved value, or when the time passed since saving differs between the clock and the wall clock (`RunState.savedAt` vs. `wallClock()`) by more than `RecordingController.rebootTolerance` (5 min). Video studies (`detectReboot: false`) never check. Run states saved before Task_47 may come from a clock that lagged after standby and can be taken for a reboot once (accepted).
  - **Order of times**: `measurementOrder` (`recording/data/measurement_repository.dart`) sorts by cycle, within a cycle by end; step timer times (cycle 0) by id, i.e. in the order they were recorded (undo re-inserts the old id), because a reboot restarts the clock. Used by `listForStudy` and the revision archive/load; `groupCycles` keeps cycle 0 in the order given.
- **Platform abstractions**: hardware volume keys (Android platform channel), speech recognition, video playback, video frame decoding and the foreground service each sit behind a Dart interface with a fake in tests. Android-only features (volume keys, recording notification) are gated by `PlatformFeatures` (`lib/core/platform_features.dart`, `platformFeaturesProvider`, derived from `defaultTargetPlatform`): on other platforms `hardwareKeysProvider` returns `SilentHardwareKeys` and `recordingNotifierProvider` returns `SilentRecordingNotifier`, and the settings hide the volume key switch, the hold slider and the notification switch.
- **External links** (`core/url_opener.dart`): `UrlOpener` (`AndroidUrlOpener`, `urlOpenerProvider`, `FakeUrlOpener` in tests) asks `MainActivity.kt` (method `openUrl` on `dev.cyclescope/platform`) to open an `https` link in the browser with an `ACTION_VIEW` intent; it returns false when no app can open it. No `url_launcher` dependency and no INTERNET permission: the app itself still makes no network call. Used by the GitHub logo in the home app bar (`study/presentation/github_logo.dart`: `GitHubLogo` paints the Octicons mark as a path in the icon theme's color, `repositoryUrl`) and the privacy policy link in the settings; a failed open shows a snack bar. On iOS the same channel (also reached through `AndroidUrlOpener`) is served by `PlatformChannel` in `ios/Runner/AppDelegate.swift`: `openUrl` opens only `https` links via `UIApplication.shared.open`, `elapsedRealtimeMicros` reads `clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW)` (deliberately not `systemUptime` or `mach_absolute_time`: those are required-reason APIs, and avoiding them means the app needs no privacy manifest); every other method returns `FlutterMethodNotImplemented`.
- **Frame decoding** (`video/platform/frame_source.dart` → `FrameDecoder.kt`, channel `dev.cyclescope/frames`): `MediaMetadataRetriever.getFramesAtIndex` (API 28+) decodes JPEG frames (longest side 1280 px) on a worker thread. `FrameCache` (pure Dart, `video/domain/frame_cache.dart`) keeps the frames within 8 of the position (forward first) and evicts far ones; `FrameTiming` converts time ↔ frame index with the real frame rate (frame count / duration). Frame stepping shows the cached frame above the player while it seeks; play or any other seek hides it. Without decoder support stepping falls back to 30 fps player seeks. iOS has no frame decoder (nothing handles `dev.cyclescope/frames`), so it always uses this fallback.
- **Data model (core)**: Study (name, description, mode) → StepDefinition (position, name) → Measurement (cycle number, step id, start, end, type `normal | special`, note). Measurements reference steps by id, never by position.
- **Groups** (`lib/group/`, migration v9): `study_group` (name, description, created_at). A study belongs to at most one group (`study.group_id`, `ON DELETE SET NULL` – deleting a group keeps its studies, unless `GroupRepository.deleteGroup(id, withStudies: true)` deletes them first, with everything that cascades from a study; the group screen's delete dialog offers this as a checkbox that is off by default, then removes the videos no other study plays via `deleteUnusedVideo` and hides the recording notification if a member was recording) at `study.group_position` (0-based order, e.g. machine order of a line). `GroupRepository` creates/updates/deletes groups, moves studies (appended at the end; null = no group) and sets the order; `StudyRepository.listStudies(groupId:)` lists the members in order and `StudySummary.groupName` names the group. `StudyRepository.copyStudy` duplicates a study with steps and times (step ids remapped), optionally into a group. "In several groups" is done by copying.
- **Nested groups / areas** (Task_38, migration v17): a group can lie in at most one parent group (`study_group.parent_id`, `ON DELETE SET NULL`) at `study_group.parent_position`; it is then an *area* of that group (e.g. one section of a large plant) and stays a full group of its own. Studies (`group_position`) and areas (`parent_position`) share one position space in their group. `GroupRepository.listMembers` gives the mixed order as `GroupMember` (sealed: `StudyMember`/`AreaMember`, `group/domain/group_member.dart`), `setParent` puts an area at the end of a group or (null) back to the top level and throws `GroupCycleException` if the target is the group itself or lies below it (depth is free); `ancestors`, `descendants` and `subtreeStudies` walk the tree; `reorderMembers(groupId, [MemberKey...], moved:)` sets the mixed order (the older `reorder(groupId, studyIds, moved:)` keeps the areas in place). `GroupSummary` adds `areaCount` (direct areas) and `totalStudyCount` (studies of the whole subtree); `studyCount` stays the direct studies. An area is always a station boundary: `stationFlags(parallel, isArea)` (`group/domain/stations.dart`) clears the flags of areas and of the member right behind one, `setParallel`/`setCellLoader` do nothing for a study right behind an area, `parallelAfterMove(..., isArea:)` reports `split` when an area is dropped inside a station (the machine behind it becomes the first of a station of its own, no loader, buffer and conveyor stay before the first part, the wait option applies to both parts as far as `tidyStations` keeps it). `StudyRepository.memberRows`/`memberStationFlags` are the mixed order for `handOverStation`, `tidyStations` and `nextGroupPosition` (new studies, copies and imports land behind the last member, area or study). Deleting a group makes its areas top-level groups; `deleteGroup(id, withStudies: true)` deletes the whole subtree (all areas below and all their studies).
- **Plant line through its areas** (Task_40): `GroupRepository.loadTree(groupId)` loads the members of a group and of every area below it; `flattenGroup(rootId, tree)` (`group/domain/group_tree.dart`, pure Dart) turns it into one line (`FlatLine`): the studies in line order, depth first, each with the path of its areas (`FlatEntry`), and the direct areas of the opened group as spans of the entries (`LineArea` group/start/end, empty area = empty span). The studies are *effective* `Study` objects (`Study.copyWith` for the line fields): the first study of an area and the first one behind an area are never parallel or a loader, whatever is stored; a cycle throws `GroupCycleException`. `loadGroupReport` uses it, so `GroupReportInput.entries` of a plant are all studies of all its areas and `LineAnalysis`, failure risk, simulation and the report builders work without special cases; `GroupReportInput.areas` holds the spans, `areaFigures` = `analyseAreas(line, parallel, areas)` (`group/domain/area_analysis.dart`): per area its stations (positions in the whole line), cycle time alone (slowest measured station – the same as the area's own line cycle time), total and lead time, output alone, waiting for the plant's pace and whether the plant's bottleneck lies in it. `LineScreen`: station numbers run through the plant, an "Areas" card (one row per direct area, tap opens that area's line analysis), area headings in the station list, area borders and names in the yamazumi chart, which scrolls sideways when the stations do not fit (`YamazumiPainter.minSlot`). A group without areas looks as before.
- **Buffer and conveyor between areas** (Task_42, migration v18): `study_group.buffer_capacity/buffer_store_us/buffer_retrieve_us/conveyor_capacity/conveyor_transport_us` = what stands before an area in its parent (`StudyGroup.hasBuffer/hasConveyor/hasLink`). It belongs to the plant, not the area: `flattenGroup` puts it on the area's first study (replacing that study's own values), the outermost link wins when an area starts with an area, it has no effect before the very first study of the line and is not passed on past an empty area; the area analysed alone never sees it. `GroupRepository.setAreaBuffer/removeAreaBuffer/setAreaConveyor/removeAreaConveyor`; `setParent` (leaving or changing the parent) and deleting the parent reset it, reordering keeps it. Line analysis, failure risk and simulation see it as `bufferBefore`/`conveyorBefore` of the area's first station (no engine change). UI: area card menu "Insert buffer/conveyor before" (not on the first member), cards above the area card (`areaBuffer_<id>`, `areaConveyor_<id>`) reuse `showBufferDialog`/`showConveyorDialog`. Backup: optional group fields `bufferCapacity/bufferStore/bufferRetrieve/conveyorCapacity/conveyorTransport` (only written for a group with `parentRef`, only read when the group is newly created inside a parent; format stays v2).
- **Simulation of a plant** (Task_43, engine unchanged): `areaSimulation(result, positions, areaFigures)` (`group/domain/area_simulation.dart`) sums a `SimResult` per area (machines, busy, blocked, down, utilization, buffer places and highest level including the buffer before the area). `SimulationScreen`: "Areas" card (`simAreas`, rows `simArea_<id>`), area headings in the station list (`simAreaHeading_<id>`), failure machines named "Area · Machine" (`areaMachine`), buffers/conveyors before an area labelled "before area X" (`beforeArea`); the line screen's failure risk rows name the area too. Runtime: `group/domain/simulation_runner.dart` – a line with more than `offThreadMachines` (30) simulated machines runs in a background isolate (`Isolate.run`; `runSimulation` for the screen with a progress bar `simBusy`, `failureScenariosOf` for the report export with a progress dialog via `withLargeScenarios`, which stores them as `GroupReportInput.precomputedScenarios`); smaller lines run directly as before. Measured (Windows desktop, debug test run): 60 stations / ~100 machines, 24 h ≈ 0.4 s, all failure scenarios of an 8-h shift ≈ 24 s; guarded in `tests/group/domain/area_simulation_test.dart` with generous limits.
- **Reports of a plant** (Task_44): the entries of a plant are already all studies of all areas (Task_40). Optional texts keep every other report unchanged: `GroupReportLabels.area` adds an "Area" column after the study in the overview (compact and full, PDF and Excel) and `LineReportLabels.areas` (`AreaReportLabels`, set by the app only when the group has areas) adds: Excel – contents with a section per area above its study sheets, an area column at the end of the line sheet's station table and of the buffer/conveyor table, an "Areas" section after the line figures (stations from–to, cycle time `MAX(C<first>:C<last>)` over the area's station rows, output per hour `IF(C>0,ROUND(3600/(C*s),1),"")`, bottleneck mark); PDF – areas on the cover, contents and bookmarks by area (area entry, its studies one level deeper), areas table and area rows in the bar chart of the line chapter, area column in the station table; failure risk rows (PDF and Excel) read "Area · Machine". `GroupReportInput.entryAreas` / `stationAreas(figures, n)` map entries and stations to their area. The path separator "›" is written as "/" in PDFs (`_latin1`). Sheet names keep "<position> <name>" with positions through the plant.
- **Splitting a group into areas and dissolving areas** (Task_45): `expandToStations` / `isContiguous` (`group/domain/area_selection.dart`) widen a selection to whole stations (a parallel machine or a loader brings its station) and check that it is a run. `GroupRepository.groupIntoArea(groupId, members, name:, now:)` creates the area at the place of the first member in one transaction (everything inside keeps its fields; what stood before the first member becomes the area's link unless the run starts the group) and refuses other selections with an `ArgumentError`; `dissolveArea(id)` puts the members back in their order (sub-areas one level up), hands the area's link to its first member and deletes the empty group. Neither changes the flattened line (`tests/group/data/group_into_area_test.dart`, including the demo line split into two areas = 1000 parts in 24 h). UI: a long press in `GroupScreen` starts a selection (`_selected`, whole stations, `clearSelection`, back ends it), the action `groupIntoArea` asks for a name and is disabled with the hint `selectionGapHint` for a gap; the area card menu has `dissolveArea` with a confirmation (`confirmDissolveArea`).
- **Crash safety**: every completed measurement and every engine state change is persisted immediately.

## App wiring

- `main()` opens the database and overrides `databaseProvider`; all other providers live in `lib/core/providers.dart` or the feature's `presentation/` folder.
- Lists are `FutureProvider`s that are invalidated after writes (sqflite has no change streams).
- Screens with live state use a `ChangeNotifier` controller (e.g. `RecordingController`) that reads its dependencies from providers once; Riverpod is the DI/override mechanism. Never use `ref` in `dispose()`.
- Platform side effects (haptics, wake lock, later keys/notifications) go through interfaces in `lib/core/platform.dart`, provided via `deviceFeedbackProvider` etc. Which recording aids the platform offers at all comes from `platformFeaturesProvider` (see Platform abstractions).
- Settings: `settingsProvider` (Riverpod `Notifier`) backed by the `settings` table; loaded in `main()` and injected via `initialSettingsProvider`. Providers that depend on settings (`deviceFeedbackProvider`, `recordingNotifierProvider`) watch it; `recordingNotifierProvider` also watches `platformFeaturesProvider`. The About section links the privacy policy (`privacyPolicyUrl`, opened through `urlOpenerProvider`).
- Wall-clock timestamps (created/active) come from `wallClockProvider`, never directly from `DateTime.now()` in widgets.
- Video studies without steps have `study.steps_open = 1` (migration v7): `RecordingController.mark()` appends a step (and rebuilds the engine from its snapshot) while on the last step; `closeCycle()` wraps to the next cycle and clears the flag (`StudyRepository.closeSteps`). With fixed steps `closeCycle()` ends the cycle early via `RecordingEngine.endCycle()` (closes the current step, next cycle starts at step 1). `StudyMode.definesStepsUpfront` says which modes ask for steps on creation. Markers may not lie before or at the last marker (`canMarkAt`, strictly after it; same position → hint `markerAtLast`, before → `markerBeforeLast`); while `steps_open`, `undoLastMarker` also deletes the steps behind the current one that have no times (the step the undone marker created; back to no steps when the start marker is undone), so `closeCycle()` is accepted again. The special time button of the video screen ends a special time on `onPointerCancel` as on `onPointerUp`. So that deleted cycles or a new video never block positions, `RecordingController.resetMarkers()` drops the open marker run (engine back to idle, stored times kept). It runs when a video study's deleted cycle contains the marker the open step started at (or is the running cycle) and whenever the video is replaced; replacing a video with recorded cycles first asks whether to delete them (`deleteAllMeasurements()`) or keep them.
- **Revisions** (`lib/revision/`, migration v10): every stored measurement gets `measurement.recorded_at` (wall clock ms from `wallClockProvider`, injected into `MeasurementRepository(now:)`; NULL for older rows). `study.revision` is the number of the current measurement round (starts at 1). `RevisionRepository.startNewRevision` archives the current steps and times into `revision` / `revision_step` / `revision_measurement` (full snapshot; `revision_step.step_id` keeps the step's id in the study, without foreign key), deletes the times and the run state and increments `study.revision` – all in one transaction; without times nothing happens. `lastRecordedAt` = newest `recorded_at` of the current times (fallback `last_active_at` for old data). `RevisionComparison.compare` (pure Dart) matches steps by id, else by name, and gives real step/cycle time deltas. `RevisionsScreen` (history icon in the recording screen, study menu in the video screen) shows the current round, starts a new one (only when idle) and the deviations of each archived revision; it pops with the new number and the screen calls `controller.load()`. `copyStudy` copies the revisions too (ids of deleted steps become negative).
- Stale measurements: `openStudy` (`app.dart`, also used by the group screens) calls `offerNewRevisionIfStale` before the screen opens. If the last measurement (`lastRecordedAt`) is older than `AppSettings.staleDays` (default 10, 0 = off; `isMeasurementStale` in `revision/domain/staleness.dart`) it asks "New measurement" (→ `startNewRevision`) or "Continue". Skipped for video studies and while a run state exists.
- **Exports and group report** (`lib/export/domain/`): `ExportInput` optionally carries the latest archived revision (`previous`) and derives `lastMeasuredAt` (newest `recordedAt`, fallback `lastActiveAt`) and `comparison`. `ExportLabels.revision` (`RevisionLabels`, optional so old call sites keep working) adds the "Revision" and "Last measurement" lines to CSV/Excel/PDF and the PDF section "Deviation from revision N". `GroupReportInput` = group + one `ExportInput` per study in group order + `GroupReportLabels`; `buildGroupXlsx` writes an overview sheet and one sheet per study (`studySheetNames`: "<pos> <name>", max. 31 chars, no `[]:*?/\`, unique), `buildGroupPdf` an overview page and every study from a new page (shared `_studyWidgets`, page numbers over the whole document). UI: `GroupExportButton` in the group screen (unit = default unit, method per study or default).
- Backup (`lib/backup/data/backup_service.dart`): JSON `cyclescope-backup` version 2 = v1 plus `groups` (ref, name, description, createdAt), per study `groupRef`/`groupPosition`/`revision`, `recordedAt` per time and `revisions` (with `steps[].stepRef` = the study's step refs, ids of deleted steps kept). v1 files still import. Merging reuses groups by name and appends imported studies behind the group's existing ones (relative order kept); replace also clears groups and revisions. Not included: run state, settings, video files. Nested groups (Task_39): optional `parentRef` (only when the parent is in the file) and `parentPosition` per group, format stays v2 (an older app imports such a file with all groups side by side). Import creates parents before their areas whatever the file order (`_parentsFirst`, which also rejects an unknown `parentRef`, a cycle or a non-numeric `parentPosition` as `BackupError.invalid` before anything is written). Validation (Task_49): `_parse` checks the type of every value the import reads before anything is written – groups (`name`, `createdAt`, optional `description` text), studies (optional `lastActiveAt`/`groupPosition` int, `revision` int ≥ 1, `description`/`notes`/`cycleTimeMethod`/`videoPath` text, buffer and conveyor fields int ≥ 0, `cellParts`/`cellMachines` int ≥ 1), times (optional `stepRef` int, `note` text, `recordedAt` int), revisions (optional `firstRecordedAt`/`lastRecordedAt` int, `cycleTimeMethod`/`notes` text) and special cycles (optional `name` text); missing optional fields stay allowed, floats count as wrong (the export writes integers). A wrong type is `BackupError.invalid`. The import button, "Open with CycleScope" (`importSharedJson`) and "Restore backup" (`BackupTiles`) show their "invalid" message for any error, so an unexpected failure (the transaction rolls back) is never silent. After restoring, `studyListProvider` and `groupListProvider` are invalidated; "Replace" with a run state hides the recording notification. Merging: a group with `parentRef` reuses the area of that name under the resolved parent; one without reuses the top-level group of that name, else the only group of that name anywhere (an area sent back by a colleague that already lies in a plant here), else it is a new top-level group. New areas and studies of a group share one offset behind its existing members; afterwards `tidyStations` runs for every touched group, so a study right behind an area is never parallel or a loader.
- **Sharing and importing studies/groups** (`lib/backup/presentation/share_actions.dart`): `exportJson(selection: ExportSelection(studyIds, groupIds))` writes the same `cyclescope-backup` file for a part of the data: the selected studies plus every study of a selected group; a selected study whose group is not selected leaves without `groupRef`. A selected group takes its whole subtree (all areas below and their studies); a selected area whose parent is not selected leaves without `parentRef` and arrives as a top-level group. `shareSelection` names the file `cyclescope_<name>_<date>.json` (`shareFileName`: the single item's name, else `studies`/`groups`) and hands it to the share sheet. `importSharedFile` picks a file (`backupPickerProvider`) and always merges (`importJson(replace: false)`), so importing the same file twice adds nothing and groups with the same name are reused. UI: long press on a study card or group starts a selection (`SelectionAppBar`: select all, share, delete; back clears it); the import button sits in the app bars of the study and group lists; single share via the study card menu and the group screen menu. Deleting selected groups asks whether to keep their studies (without group) or delete them too (`deleteStudies` also removes unused video files). `deleteStudies` (also used by the study card's "Delete") hides the recording notification when one of the deleted studies is the run saved last (`RunStateRepository.activeRuns().first`, the one the notification shows); deleting another study keeps it.
- **Open with CycleScope** (`backup/platform/incoming_files.dart`, no extra package): `IncomingFiles` (`PlatformIncomingFiles`, `incomingFilesProvider`, `FakeIncomingFiles` in tests) on channel `dev.cyclescope/incoming_files`. The native side keeps the text of each received file until Dart calls `takeIncomingFiles` (on listen) and calls `filesWaiting` when another arrives while the app runs, so cold start and running app work the same. `StudyListScreen` (home) listens and imports each file with `importSharedJson` (merge, result snackbar). Android (`MainActivity.kt`): intent filters for `ACTION_VIEW` (scheme `content`) and `ACTION_SEND` with `application/json` and `application/octet-stream` (mail and messenger attachments), file read on a worker thread, max. 32 MB, not again after a configuration change. iOS (`AppDelegate.swift`): `CFBundleDocumentTypes` for `public.json` (rank Alternate, `LSSupportsOpeningDocumentsInPlace` false), `IncomingFiles` holds the files, `IncomingFilesSceneDelegate` (a `FlutterSceneLifeCycleDelegate` added with `addSceneDelegate`) takes URLs from `connectionOptions` at launch and from `openURLContexts`; XCTests in `ios/RunnerTests/RunnerTests.swift`.
- **Line analysis** (`group/domain/line_analysis.dart`, pure Dart): `LineAnalysis.of(stations)` looks at a group as a line in group order – sum of the station real cycle times (processing lead time, no buffers), line cycle time = bottleneck (max), balance = sum / (measured stations × bottleneck), output per hour, waiting time per station, step segments scaled to the station cycle time, comparison with the previous revisions (only if every measured station has one). Stations without complete cycles (step timer, no times) are listed but not counted. `GroupReportInput.line` builds it from the report data; `loadGroupReport()` (`export_menu.dart`) loads the data for the report and the `LineScreen` (key figures, `YamazumiPainter` stacked bars with dashed bottleneck line, station list), opened from the group screen.
- **Excel look** (`lib/export/domain/xlsx_layout.dart`): every sheet of every workbook is written through `SheetLayout` (`title`, `section`, `note`, `keyValue`, `cells`, `header`, `row(total:)`, `gap`, `finish`). It owns the row cursor and the look: Calibri 11, brand-coloured title/section headings, bold key-figure labels, table headers in white on the brand colour `0B6B8A`, banded rows with thin grey borders, a tinted bold total row, blue underlined links (`sheetLink`), row heights, real empty rows between blocks (`gap`; `appendRow([])` of the excel package is a no-op) and column widths from the measured content (min 9, max 50; table texts over 46 characters are measured as 46 and wrap only when `finish` finds them wider than their final column – an average text character counts as 0.9 of the "0" Excel measures widths in – so only rows that really need more lines get higher; long key-figure texts and notes overflow instead of widening a column, except on a sheet without tables (nothing right of column B, e.g. Contents), where they widen column B up to 60 and wrap beyond that). Numbers get fixed decimals via `fixed(value, decimals)` (times: 3, HM: 2, TMU/percent: 1); headers of number columns are right-aligned (a column without values counts as numbers when its title ends with a unit `]`). Key-figure numbers use the format `0.000* ` (fill of spaces) so they stand left like texts – the excel package cannot write a left alignment. Other quirks of excel 4.0.6 handled there: the `CellStyle` constructor ignores `underline` (set by the setter), and `updateCell` resets the style, so value and style are always written together. New sheets must use `SheetLayout`, not `appendRow`.
- **Complete group report** (Task_25): `buildGroupReportPdf` = cover (group, line key figures) with a clickable table of contents (page numbers, `pw.Link` to `pw.Outline` anchors, which are also PDF bookmarks), line analysis (bars per station, station table), overview and every study from a new page. The document is laid out twice: pass 1 records the first page of every section (`doc.document.pdfPageList.pages.length` after each `addPage`), pass 2 prints them. `buildGroupReportXlsx` = sheets Contents (`HYPERLINK("#'sheet'!A1", ...)` formulas), Line analysis (station cycle times as references to the real cycle time cell of each study sheet, share/waiting/Δ, SUM, MAX, INDEX/MATCH bottleneck, balance, output per hour as formulas), Overview (extra link column) and the study sheets (back link in row 1). The excel package writes formulas without cached values; Excel/LibreOffice compute them on opening. Row numbers for formulas come from `SheetLayout` (`nextRow`, return value of `keyValue`/`row`), never from `maxRows`. The compact builders `buildGroupPdf`/`buildGroupXlsx` stay as the "compact" export option.
- **Parallel machines** (migration v11): `study.parallel` = works in parallel with the group member before it; consecutive parallel members form one station (`stationGroups`, labels "2a/2b" via `stationLabels` in `group/domain/stations.dart`). `GroupRepository.setParallel`; moving into/out of a group and copying reset the flag; backup field `parallel` (optional, format stays v2). A "machine with fixed cycle time" (`MachineService`, `machineServiceProvider`) is a simple study with exactly one lap of the typed duration (`parseTimeInput`, unit = default unit, stopwatch typed as seconds); "Enter cycle time" archives the previous times as a revision and stores a new lap.
- **Parallel stations and failure risk** (Task_27): `LineAnalysis.of` builds stations from consecutive parallel inputs (`LineStationInput.parallel`, `stationGroups`). A station holds its `LineMachine`s; its effective cycle time is `parallelCycleTime` = 1 / Σ(1 / machine cycle time) over the measured machines, its `leadTime` the mean machine cycle time (one part passes one machine) – unless the station waits for its slowest machine, see below. `totalTime` = Σ effective station times (basis of share and balance), `leadTime` = Σ station lead times. `FailureRisk.of(line)` (pure Dart) gives, per measured machine, the line output while it is down (minimum station capacity, a station without a remaining machine → 0 = standstill) and the loss, sorted by loss; `singlePoints` = stations whose only machine stops the line. `LineScreen` shows lead time, machines per station ("×n" in the bar) and the failure risk list.
- **Reports with parallel stations and failure risk** (Task_28): the Excel line sheet has one row per station (`stationGroups` over the entries); a parallel station's cycle time is the formula `1/(1/'sheet a'!B8+1/'sheet b'!B8+...)`, its name the machine names with "(×n)". `LineReportLabels.risk` (`RiskReportLabels`, optional) adds the failure risk sheet (Excel, linked from Contents) and chapter (PDF, in the table of contents) built from `FailureRisk`. The app adds them when the line has at least one parallel station.
- **Buffers** (migration v12): a buffer before a station is stored on the station's first member (`study.buffer_capacity` 0 = none, `buffer_store_us`, `buffer_retrieve_us`; `Study.hasBuffer`). Never before the first station. `GroupRepository.setBuffer/removeBuffer`; switching a member to parallel, moving and copying drop it (the first machine of a parallel station hands it to the next one, see "Stations stay together"); backup fields `bufferCapacity/bufferStore/bufferRetrieve` (optional, format v2). The group screen shows the buffer as its own card above the station (tap = edit/remove, `showBufferDialog`), menu item "Insert buffer before". Semantics (simulation, Task_30): the buffer stores only on a jam, its own machine spends the store/retrieve time, and it empties itself when the next station is free.
- **Line simulation** (`group/domain/line_simulation.dart`, pure Dart, Task_30): deterministic event-driven simulation of `SimStation`s (machines with their real cycle time, parallel machines share the work; of several free machines the fastest takes the next part, and of parts finished at the same time the fastest machine's moves on first, so the order of parallel machines never changes the result) over a horizon. Raw parts are unlimited, the line starts empty, there is no space between stations without a buffer (a finished part blocks its machine). A `SimBuffer` before a station is its own machine with one place in front of the station: it stores a waiting part only on a real jam – the station cannot take the part before the buffer could have stored and retrieved it (`takeTimes` estimates when the station takes its next parts: its machines in the order they become free, each again one cycle later; a machine blocked with a finished part counts as free when the station behind it takes that part) – otherwise it brings stored parts to the place in front of the station while it works; that part goes before parts on the conveyor. A part that the station can take sooner is never stored, so a slow buffer does not slow the line down (property tests in `tests/group/domain/buffer_rule_test.dart`). `SimFailure` = one machine down from a start time for a duration (a part in work finishes after the repair). `run` takes an optional `failure` plus a list `failures`; all are stop windows like planned stops (stops of the same machine that overlap – failures and planned stops – are merged, so overlapping time counts once; a part in work is delayed only by the time a stop adds). `SimResult`: output, per station busy/blocked/down time and utilization, per buffer max/end level, stores, retrieves, handling time. `failureScenarios` compares every machine failure with and without buffers. `LineSimulation.fromLine(LineAnalysis)` takes the measured stations; `LineStationInput.buffer`/`LineStation.bufferBefore` (`LineBuffer`) carry the buffers. A 24 h run with ~7000 parts and all scenarios takes well under a second. Time accounts: every machine keeps its stops as merged intervals; stopped time is neither busy nor blocked time (busy and blocked are counted without the stops inside them, all clipped to the horizon), so busy + blocked + down never exceed the period. `run` throws an `ArgumentError` for a machine with a cycle time ≤ 0 (it would finish parts without time passing); `LineAnalysis` treats a real cycle time below 1 µs as "not measured", so `fromLine` never produces one, and `parseTimeInput` rejects typed times below 1 µs.
- **Simulation screen** (Task_31): `SimulationScreen` (play icon in the line screen) runs `LineSimulation.fromLine(loadGroupReport(...).line)` over a shift (`AppSettings.shiftMinutes`, default 480), 24 h or a free number of hours, optionally with one or more machine failures (rows of machine, start in hours, default a quarter of the period, and duration in minutes, default `AppSettings.failureMinutes` = 30; "Add failure" appears once the first row has a machine, a new row starts on the machine of the one before and is removed with its × button; choosing "No failure" in the first row drops all rows). The failures are screen state only, not stored. Stations are labelled with their number in the line (stations without times are not simulated but keep their number). It shows parts without/with the failures, lost parts, lost parts without buffers and the parts saved by the buffers, per buffer fill/moves/handling time and per station utilization, blocked and down time (`formatDuration`). The line screen lists buffers between the stations. Limits (Task_50): the free horizon is at most `maxHorizonHours` (720 h = 30 days; a larger value shows `simHorizonTooLong` and keeps the previous results, like an invalid time; measured: a small line needs ≈ 0.5 s for 720 h with a failure and a buffer in a debug test run). The screen runs through `simulationRunnerProvider` (`SimulationRunner` in `group/domain/simulation_runner.dart`: `offThread`, `run` on the UI thread, `runInBackground` in an isolate; replaced in tests); if a calculation throws on either path, the progress bar `simBusy` ends, the results go and `simFailed` is shown; the next run starts normally.
- **Reports with buffers and simulated risk** (Task_32): `GroupReportInput.simulationHorizonMicros/simulationFailureMicros` (the app passes shift length and assumed failure duration from the settings) give `failureScenarios` (only when the line has buffers; failure after a quarter of the period). `LineReportLabels.buffers` (`BufferReportLabels`) adds a buffer table to the line chapter/sheet; `RiskReportLabels.withSimulation` adds the columns "lost without/with buffers" and a note to the failure risk chapter/sheet. The app adds the failure risk when the line has parallel machines or buffers.
- **Conveyors** (Task_33, migration v13): `study.conveyor_capacity` (0 = none) and `conveyor_transport_us` on a station's first member (like the buffer; dropped on parallel/move/copy; backup fields `conveyorCapacity/conveyorTransport`). `LineConveyor`/`LineStation.conveyorBefore`; the lead time of one part includes the transport times. Simulation: `SimConveyor` is a FIFO with a capacity counting moving and jammed parts; a finished part leaves its machine while there is room and reaches the next station after the transport time. With a conveyor, a buffer at the same place stands at the station: it stores only when the conveyor is full and jammed (same jam rule as above) by taking the part at the end of the conveyor, which makes room for the next finished part, and brings a stored part to the place in front of the station once no part waits at the end of the conveyor. Every part travels the conveyor, so the output never exceeds capacity / transport time. `withoutBuffers()` keeps the conveyors. Group screen "Insert conveyor before", conveyor cards in group, line and simulation screens, conveyor columns in the report's connection table (`BufferReportLabels.conveyorPlaces/conveyorTime`).
- **Special cycles and planned stops** (Task_34, migration v14): table `special_cycle` (study, name, kind `parts`/`time`, interval = parts or µs, duration µs), `SpecialCycleRepository` (`specialCycleRepositoryProvider`), copied with the study and part of the backup (`specialCycles`). `effectiveCycleTime(base, cycles)` = (base + Σ duration/N) / `availability` (1 − Σ duration/interval). `LineStationInput.specialCycles` → `LineMachine.cycleTime` is the effective time, `baseCycleTime` the measured one; line figures and the failure risk use the effective time. Simulation: `SimMachine.specialCycles` – every N-th part takes the extra time; planned stops are stop windows like a failure, the first after half the interval, then every interval. `GroupReportInput.specialCycles` (per study id, loaded by `loadGroupReport`). UI: member menu "Special cycles & stops…" → `SpecialCyclesScreen`; reports list them with measured and effective cycle time (`SpecialReportLabels`). The Excel line sheet writes a machine's station cycle time as `(study cell + extra time per part) / availability` (`extraPerPart`, `availability` as constants in the report unit), so its line figures match the app and the PDF. The dialog rejects a planned stop that is not shorter than its interval (`stopTooLong`).
- **Loader cells** (Task_37, migration v15): a station whose machines are served in turn by loaders on a shared rail (gantry loaders). Data: `study.cell_loader` (a loader of the station it belongs to; only valid together with `parallel`, see `Study.isCellLoader`), `study.cell_parts` (parts a loader handles per own cycle) and `study.cell_machines` (number of equal machines a non-loader member stands for), all only used when the station has a loader; `step_definition.waiting` marks a step as waiting for supply (a machine, material). Loaders are attached to their station through the existing `parallel` flag, so `stationGroups`, `parallelAfterMove` and `handOverStation` keep the cell together without a second grouping logic: `GroupRepository.setCellLoader` sets both flags (and drops buffer/conveyor like `setParallel`), `setParallel` always ends the loader role, a member that becomes a station of its own (reorder, hand-over) loses it, moving to another group and copying reset all three fields. A plain parallel member inside a cell is another machine type of it. `StudyAnalysis.workCycleTime` = real cycle time without the waiting steps (`waitingStepIds` lets an archived revision use the marks of the current steps, see `ExportInput.previousAnalysis`); the study's own figures stay unchanged, the step editor (hourglass toggle) and the analysis only show the mark. `LoaderCell.of` (`group/domain/loader_cell.dart`, pure Dart): every loader touches every part, the machines share the parts → cell cycle time = max(loader work time / parts per cycle, 1 / Σ(count / machine work time)); bottleneck, utilization, waiting time per own cycle, and for one machine type the table for 1–6 machines (`options`) and `bestMachineCount` = ⌈machine time / slowest loader⌉. Waiting for another loader on the rail is deliberately *not* marked: it belongs to the loader's cycle. Not measured unless a machine and a loader have times. `LineAnalysis.of` turns a station with a loader (`LineStationInput.cellLoader/cellParts/cellMachines`) into a cell: `LineStation.cell` holds the `LoaderCell`, `machines` has exactly one entry named after the machines with the cell cycle time (special cycles of the members are already inside the work times, so `baseCycleTime` = `cycleTime` and it carries no rules), `leadTime` = machine time. Failure risk, simulation (`LineSimulation.fromLine`) and reports therefore treat the cell as one machine; buffers and conveyors around it work unchanged. UI: member menu "Loader of the machine above", "Number of machines…" / "Parts per cycle…" (`showCellCountDialog`), role in the member subtitle; `LoaderCellCard` under the station in the line screen (resources, machine table, measuring hint). Reports: `LineReportLabels.cells` (`CellReportLabels`) adds one section per cell to the line sheet/chapter; the Excel station row of a cell is a value, not a formula (the work times are not on the study sheets). Backup fields `cellLoader/cellParts/cellMachines` per study and `waiting` per step (optional, format stays v2). Not modelled: what-if on the rail interlock (who waits for whom), failures of single machines of a cell.
- **Demo data** (`lib/demo/`, Task_35): `DemoDataService.load(DemoTexts)` adds a sample line through the normal repositories only (no own SQL, no migration): group "Demo: housing line" with 15 members / 8 stations – saw (typed 57 s, blade change every 8 h), the loader cell (`_loaderCell`, station 2: one lathe time study standing for 3 machines, occupied ≈ 88 s per part, last step "wait for the loader" marked as waiting; loader 1 as a time study, ≈ 32 s without the marked "wait for the machine" while "wait for loader 2" on the rail counts – the bottleneck of the cell, so a fourth machine would bring nothing; loader 2 as a time study, ≈ 20 s, "wait for the magazine" marked; the magazine loader typed 15 s; with ≈ 32 s per part the cell is far faster than the line and does not change its pace), milling centre 1 (time study, revision 1 archived, special time, special cycles) parallel to milling centre 2 (typed 167 s, bottleneck station, buffer before), washer (conveyor before), cover press (typed 52 s) and seal cutter (typed 38 s) in parallel as a station that waits for its slowest machine (their parts are joined in the assembly), assembly (time study with an outlier, IQR method, revision, special time), test benches 1–3 in parallel (buffer before, calibration every 200 parts), packing (simple study with laps, conveyor before) – plus a step-timer changeover study outside the group. Since Task_46 the housing line is an area of the plant "Demo: plant" (`DemoTexts.plantName`), followed by the area "Demo: shipping" (labeler 35 s, palletizer 40 s, both typed) with a conveyor before it (6 places, 45 s); `load` still returns the housing line's id. The housing line is the plant's bottleneck area; the whole plant makes 998 parts in 24 h (`tests/demo/demo_plant_test.dart`). One plant shows every feature. The times are tuned so that the simulation of 24 h without a failure gives exactly 1000 parts (line cycle time ≈ 85.7 s, 42 parts/h; the test in `tests/demo/demo_data_service_test.dart` pins this – after a change to the simulation rules re-tune the milling times). Times are deterministic, timestamps relative to `wallClockProvider` (current times 1–2 days old, so no stale prompt). Names come from l10n (`demoTextsOf(AppLocalizations)`), i.e. the app language at load time. Settings → Data → `DemoDataTile` (confirmation dialog, invalidates the study and group lists). Each load adds a new copy; nothing is replaced.
- **Stations stay together** (review after Task_35): "parallel" means parallel to the member before, so every way a member leaves its place must look after the members behind it.
  - Leaving the group (`GroupRepository.moveToGroup`, `StudyRepository.deleteStudy`) calls `StudyRepository.handOverStation`: if the member is the first machine of a station with parallel machines, the next machine becomes the first one and takes over the buffer and conveyor (`stationLinkColumns`).
  - Reordering: `GroupRepository.reorder(groupId, ids, moved: id)` (the group screen always passes the moved member) applies `parallelAfterMove` (`group/domain/stations.dart`, pure Dart): a first machine that moves away hands its station over as above; the moved member is parallel only when it was dropped inside a station (the member behind it is parallel) and then loses its own buffer/conveyor; anywhere else it is a station of its own. Without `moved` only the positions change.
- **Stations that wait for their slowest machine** (migration v16): `study.wait_for_slowest` (`Study.waitForSlowest`, `StudyRepository.waitColumn`) on the first member of a station with several machines. Default (off): the parallel machines share the work and their capacities add up. On: each machine makes a part of one unit (e.g. five parts that are joined afterwards), so the station is done when its slowest machine is done.
  - Data: `GroupRepository.setWaitForSlowest(studyId, wait)` takes any machine of the station and writes the first one. The option travels with the station: `handOverStation` and `reorder` hand it to the next machine when the first one leaves (also for the first station of the line, unlike buffer and conveyor), a member switched back to serial keeps it for itself and the machines behind it. `StudyRepository.tidyStations(db, groupId)` (`handOverStation` returns the group to tidy) drops it wherever it has no meaning (not the first machine, a station with one machine, or a loader cell – `setCellLoader` calls it too, and the menu item is not offered there) and runs after every change of the stations (`moveToGroup`, `deleteStudy`, `setParallel`, `reorder`), so a station never starts waiting again because of a forgotten flag. Copying resets it; backup field `waitForSlowest` (optional, format stays v2).
  - Line analysis: `LineStationInput.waitForSlowest` → `LineStation.waitsForSlowest` (only with several machines); cycle time and lead time of the station = `slowestCycleTime` (maximum of the measured machines), also for the previous revision. `FailureRisk`: every machine of such a station stops the line, and the station counts once in `singlePoints`.
  - Simulation: `SimStation.waitForSlowest`. In `run` the machines of such a station form one `_Joint` (a `_Machine` whose `workers` are the machines): it takes one part when all machines are free and none is stopped, all start together, and the part moves on when the last one is done (`doneAt`; a stop of one machine only delays the station when that machine becomes the last). Dispatching, `takeTimes` and the event loop work on `units` (machines or joints); stops and the time accounts stay per machine (a machine that is done early is neither busy nor blocked while it waits for the others).
  - UI and reports: checked menu item "Wait for the slowest machine" (`toggleWaitForSlowest`) on every member of a station with several machines, a note on the first machine's card (`stationWaits_<id>`); line screen text `lineWaitingMachines` and "3→1" instead of "×3" in the bar. Excel line sheet: station formula `MAX(...)` instead of `1/(1/a+1/b)`, name `A / B (2, waits for the slowest)` (`LineReportLabels.waitsForSlowest`, optional; without it `(2→1)`); the PDF adds the text to the station name.
- **Video files** (`video/platform/video_files.dart`): `VideoFiles` (`LocalVideoFiles`, `videoFilesProvider`, `FakeVideoFiles` in tests) deletes copied videos. `deleteUnusedVideo` (`video/data/video_cleanup.dart`) deletes a file only when no study uses its path any more (copies of a study share the file); called after deleting a study, after replacing a video (once the player has opened the new one) and when the "keep cycles?" question is cancelled (the copy made by the picker). Replacing (Task_48): nothing changes before the player has opened the new file – only then are the times deleted (if chosen), the markers reset, `study.video_path` saved and the old file removed; an unplayable new file is removed again and `videoNotPlayable` is shown, the old video and its times stay. `PluginVideoPlayback.open` releases the previous `VideoPlayerController` only after the new one is initialized and releases the new one if that fails, so the old video keeps playing and no controller stays open. `study.video_path` stores the form `videos/<file>` relative to the documents folder (`VideoPaths` in `video/platform/video_paths.dart`, `videoPathsProvider`): `FileVideoPicker` returns it, the video screen and `LocalVideoFiles` resolve it at read time, because the absolute path of the iOS app container changes with every app update. Legacy absolute paths into a `videos` folder (older studies, backups) that no longer exist are found by file name in the current videos folder; there is no DB migration.
- **Fresh times carry their timestamp**: `MeasurementRepository.store` returns the stored `Measurement` including `recordedAt`; `RecordingSession` uses it, so exports right after recording show the right "last measurement". Anything that copies a `Measurement` (`updateNote`, `moveBoundary`) must pass `recordedAt` on.
- **Undo of a marker with special times**: `RecordingEngine.rewindTo(m, specials:)` continues behind the last special time of the step with the time worked before it, so the special time is not counted into the step again; `RecordingController.undoLastMarker` passes the special times of that step.
- Groups UI: home app bar → `GroupListScreen` → `GroupScreen` (reorderable list with drag handles plus "Move up/down" in the item menu, add new/existing studies, move/copy/remove). Shared dialogs in `group/presentation/group_dialogs.dart` (`pickGroup`, `moveStudyToGroup`, `copyStudyToGroup`); the study card menu on the home screen uses them too. `OpenStudy` callbacks are passed down from `app.dart`. Areas (Task_41): `GroupScreen` lists studies and areas in one reorderable list (`MemberKey` order, `reorderMembers`); an area card (`area_<id>`, menu `areaMenu_<id>`: up/down, move to group, "Remove from group" (`detachArea`, makes it a top-level group again), dissolve; deliberately no delete, so a group is never deleted from inside its parent – delete it from its own screen or the group list) shows its station range numbered through the plant ("2–4", from `loadGroupReport`/`areaFigures`, only loaded when the group has areas), its studies and cycle time, and opens the area's own `GroupScreen`. The add sheet (scroll-controlled) offers "New area" (created and opened) and "Add existing group" (top-level groups except the group itself and its ancestors). A study right behind an area has no "parallel"/"loader" menu items. - Study notes: `study.notes` (migration v8, `TEXT NOT NULL DEFAULT ''`), edited in the analysis tab via `RecordingController.setNotes()` (which also refreshes `study`, so an export right after typing sees them) and written by the CSV/Excel header block and the PDF report; part of the backup (`notes`, optional on import). ## Environment

- Dependencies only via `flutter pub add` / `flutter pub get`. No `.env` needed (no external services).
- Release signing: the signing key is the only secret needed to build locally. `android/app/build.gradle.kts` signs release builds with the key from `android/key.properties` (template: `android/key.properties.example`; the real file, `*.jks` and `*.keystore` are git-ignored). Without the file, release builds use the debug key.
- The release keystore lives outside the repository and must be backed up by the owner: without it no update of an installed app is possible. GitHub secrets used by `.github/workflows/release.yml`: `ANDROID_KEYSTORE_BASE64` (base64 of the `.jks`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
- Releases: pushing a tag `vX.Y.Z` runs the tests, builds `flutter build apk --release` (version name from the tag, version code = workflow run number) and publishes the APK as a GitHub release.
- Google Play: application ID `dev.cyclescope.cyclescope` (fixed once published), launcher label `CycleScope`. Upload an app bundle (`flutter build appbundle --release`, signed with the release key above as upload key; Play App Signing holds the app signing key). Store graphics (Google Play and App Store) are made in two steps: `flutter test tests/screenshots/store_screenshots_test.dart --dart-define=STORE_SCREENSHOTS=true` renders the app screens with the demo line into `store/raw/<phone|tablet>/<lang>/`, then `python tool/generate_store_assets.py` puts them under captions into device frames in every store size (Play phone 1080 × 1920, tablet 2064 × 2752, feature graphic 1024 × 500, icon 512; App Store iPhone 6.9" 1320 × 2868, 6.5" 1284 × 2778, iPad 13" 2064 × 2752, icon 1024) inside the local, git-ignored `store/` folder (listing texts and console answers are kept there by hand).
